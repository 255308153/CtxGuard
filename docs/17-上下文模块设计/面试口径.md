## 1. 三十秒极简版（被问"介绍一下你的上下文优化网关项目"时）

> "在做 Agent 和多轮代码生成时，我发现上下文开销存在两个核心痛点：一是重复文件读取和臃肿工具输出导致 **Token 消耗指数级膨胀**；二是很多压缩工具乱改历史文本，导致**破坏了厂商的 Prompt Cache**，反而让账单翻倍。
> 
> 为此我设计并实现了 **CtxGuard**——一个极致轻量（0 重型依赖、单文件免运维、<3ms 转发延迟）的上下文守护代理网关。
> 
> 核心做成了四件事：
> 1. **第一性原理守护 Prompt Cache**：通过反向推导 Token 冻结边界与字节级绝对防抖，确保命中 Anthropic/DeepSeek 90% 的缓存折扣；
> 2. **可逆无损压缩（CCR）**：基于 SHA-256 内容指纹去重，向大模型注入 `ctx_expand` 虚拟工具并由网关本地 0 Token 拦截展开；
> 3. **结构化算子流水线**：实现了 JSON 数组 Schema 折叠、ANSI/终端进度条合并与堆栈折叠，无损节省 40%~60% 冗余；
> 4. **离线失败自进化**：后台异步挖掘 Agent 死循环与因果转折点，自动幂等更新本地规则文件（如 `CLAUDE.local.md`）。"

## 2. 核心技术高频追问标准答案

### Q1：为什么强调「Cache > Compression（缓存优于压缩）」？

> "因为大模型供应商的计费模型变了。
> 
> 以 Anthropic 和 DeepSeek 为例，命中古代前缀缓存可以享受 **90% 的读取折扣**（只需 0.1 倍价格）；而如果缓存未命中写入，还要付出 **25% 的写入惩罚**（1.25 倍价格）。
> 
> 假设你有一段 10,000 Token 的历史上下文：
> - **如果不乱动前缀，命中缓存**：成本为 `10,000 * 0.1 = 1,000` 计费 Token。
> - **如果盲目用压缩算法把它压成了 5,000 Token**：由于改动了中间的一个字符，导致前缀哈希全废，云端按未命中全量计算：成本为 `5,000 * 1.0 = 5,000` 计费 Token。
> 
> **结果是：你辛辛苦苦压掉了 50% 的 Token，账单反而贵了 5 倍！**
> 
> 所以在 CtxGuard 中，**压缩是手段，缓存安全才是目的**。我们建立了**经济套利仲裁器**：只有当压缩节省率 `savings_fraction > read_discount` 时，才允许打破缓存，否则绝对维持前缀字节级不可变。"

### Q2：可逆压缩（Reversible Dedup）中，大模型如果调用展开，怎么做到 0 Token 往返？

> "我们在网关层做了**虚拟工具本地短路拦截（Virtual Tool Local Interception）**。
> 
> 1. 当 Agent 第一次读取大文件时，CtxGuard 在本地 SQLite 记录文件全文的 SHA-256，请求放行；
> 2. 当后续轮次重复出现该文件时，将其替换为紧凑引用标：`[Ref:sha256_e4d909 | File: src/main.py | 350 lines unchanged]`；
> 3. 网关自动在 Tools 列表注入 `ctx_expand(ref_id)` 声明；
> 4. 当模型确实需要查阅细节时，它会触发 `tool_use: ctx_expand`。**这个请求在进入 CtxGuard 时被立即拦截，直接从本地 SQLite 读出原文组装成 tool_result 返回给模型，根本不向上游云端大模型转发这一轮开销**。
> 5. 这样实现了：平时省 95% Token，需要时 1ms 0 Token 还原。"

### Q3：工具列表反复增删导致的「Tools Flipping」问题你们怎么解决的？

> "这是一个极其隐蔽的 Prompt Cache 破坏坑。
> 
> 最早的做法是：'只有当前轮次发生了压缩，才向 `tools` 注入 `ctx_expand`'。
> 这会导致一个致命现象：
> - 第 1 轮：没压内容 → `tools = [read, grep]`
> - 第 2 轮：压了内容 → `tools = [read, grep, ctx_expand]`
> - 第 3 轮：没压内容 → `tools = [read, grep]`
> 
> 整个 `tools` 列表在两个状态间反复翻转。因为 `tools` 位于 Prompt 的头部稳定区，它的字节一变，**导致从 `tools` 往后的所有历史对话全部 Cache Miss**。
> 
> CtxGuard 的解法是 **Sticky-On（一次开启，会话级永久保持）**：只要当前会话发生过一次可逆压缩，`ctx_expand` 工具在后续所有轮次强制挂载，绝不允许工具签名抖动。"

### Q4：为什么你们不做重型向量库，而是选 SQLite + FTS5？

> "这是为了坚持**极致轻量、零外部运维依赖（Zero Heavyweight Dependencies）**的工程原则。
> 
> 1. Agent 本地运行时，开发者绝不愿意在本地再启动 Docker、Milvus、Redis 或 PostgreSQL；
> 2. SQLite 在开启 `WAL` 模式后，单连接只读性能超过 50,000 QPS，写入仅需毫秒级，且内嵌 FTS5 全文检索引擎，支持基于 BM25 的代码符号与关键词快速检索；
> 3. 对于代码实体关系，我们构建了 **2 跳 BFS 子图遍历**，配合 `valid_from` / `valid_until` 的**事实版本演化链（Supersession Chain）**，单文件 SQLite 就能完美承载数万条实体与会话记忆，开销只有几十 KB，比 Chroma/Milvus 快一个数量级且启动 0 延迟。"

## 3.  架构师/高级岗位加分项：聊系统边界与分工

被问到“给你一个 3~5 人的小团队，你会如何演进和分工这个上下文网关系统？”时：

> "如果带团队演进 CtxGuard，我会把人员清晰拆分为三条线：
> 
> 1. **网关核心与协议层（1人）**：专精 HTTP/SSE 高性能流式代理、SIMD 序列化（orjson）、OpenAI/Anthropic/Gemini 协议对齐、以及多模型 Prompt Cache 行为探针；
> 2. **算子与智能自适应流水线（1~2人）**：专精 AST 代码语法剪枝、JSON 表头自适应折叠、ONNX INT8 微型双向编码器轻量打分、以及基于 Bandit 的动态压缩档位调度；
> 3. **记忆图谱与离线自进化引擎（1人）**：专精单文件时序图谱、因果转折点挖掘、规则自动收敛与防退化评测。
> 
> **核心原则**：业务 Agent 逻辑千变万化，但**上下文的结构治理、前缀防抖和成本监控应该下沉为通用的基础设施**。绝不能让业务同学在每个 Agent 里手工拼凑 Prompt 截断逻辑。"
