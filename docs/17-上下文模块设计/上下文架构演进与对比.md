## 二、 关键技术选型深度剖析

### 1. 为什么不直接采用 LLMLingua-2 默认架构？

- **LLMLingua-2 的优势**：利用微型双向编码器对 Token 进行重要性二分类，文本信息密度高。
- **痛点与代价**：
  1. **冷启动与内存重**：引入 PyTorch/Transformers 使得镜像体积膨胀 2GB+，本地无法即启即用；
  2. **破坏代码语法与 Prompt Cache**：对 Python/JSON 等结构化数据丢词可能导致 `SyntaxError` 或括号不匹配，且前缀改写直接摧毁 Prompt Cache。
- **CtxGuard 的折中解法**：
  - 默认采用**纯启发式规则算子（AST + 正则 + JSON 矩阵重排）**，0 依赖秒级启动；
  - 仅将语义打分作为可选插件（基于 `onnxruntime-cpu` INT8 导出，仅 30MB 且无需 PyTorch），在超长上下文阶段才按需触发。

### 2. 为什么选择 Headroom 风格的透明代理，而非纯 SDK 库？

- **透明代理优势**：
  1. **零代码改造**：开发者的 Cursor / Claude Code / Python 脚本只需将 `base_url` 改为 `http://127.0.0.1:8787`，即刻接入；
  2. **双向生命周期拦截**：代理层能够同时监控**出站 Prompt 压缩**与**入站 SSE 流式响应**，并在模型调用虚拟工具（如 `ctx_expand`）时直接本地短路执行，纯 SDK 模式无法透明拦截模型工具调用。

### 3. 与 TokenPilot (EMNLP 2026) 的理念共鸣

- **TokenPilot 核心洞察**：大模型成本瓶颈不在总 Token 数，而在**上下文的前缀连续性**。
- **CtxGuard 落实机制**：
  - 建立 **Dynamic Token Boundary（动态冻结边界反向映射）**；
  - 引入 **Economic Arbitrator（经济套利仲裁器）**：仅在 `(raw - compressed)/raw > read_discount` 时才考虑打破缓存。
