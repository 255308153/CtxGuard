# 00 · 架构总览

## 一、 它是什么

`CtxGuard` 是一个高性能、本地化运行的 **LLM 上下文智能守护与优化代理网关**。它插在客户端（Cursor、Claude Code、Python Agent SDK）与云端大模型 API（Anthropic Claude、DeepSeek、OpenAI）之间。

```text
客户端 (Cursor / Claude Code / Agent SDK)
       │  发送标准 HTTP 请求 (包含完整 system, messages, tools)
       ▼
┌──────────────────────────────────────────────────────────┐
│  CtxGuard 本地网关 (运行于 127.0.0.1:8787，数据完全不出机器)   │
│  ① 协议归一化 → ② 指纹去重 → ③ 结构压缩 → ④ 缓存冻结守护     │
└──────────────────────────────────────────────────────────┘
       │  转发经过极致优化且前缀对齐的 Payload
       ▼
云端大模型 API (Anthropic Claude 3.5 / DeepSeek V3 / OpenAI GPT-4o)
```

**CtxGuard 的核心原则**：
- **不改动大模型权重，不依赖重型推理框架**；
- **在请求侧改写 HTTP Request Body**，实现当天上线、立即见效；
- **0 外部重型依赖**：不依赖 Docker、Redis、PostgreSQL、Milvus，依靠纯算法、orjson 与单文件 SQLite。

## 二、 它在技术栈中的分层定位

在 LLM 上下文工程中，通常存在三个层次的优化：

| 层次 | 优化手段 | 代表技术/框架 | 落地门槛与代价 |
| :--- | :--- | :--- | :--- |
| **模型算法层** | 修改 Attention 机制、长上下文微调、MoA | 研究论文、FlashAttention | 需重新预训练/微调，成本极高 |
| **推理引擎层** | 操作 KV Cache 张量、前缀共享、PagedAttention | vLLM、SGLang、LMCache | 需自建 GPU 推理集群，无法作用于闭源 API |
| **应用请求层 (CtxGuard)** | **在 HTTP 代理层治理 Prompt 结构、前缀对齐与去重** | **CtxGuard**、Headroom | **即插即用、零侵入适配公有云闭源 API 与私有模型** |

CtxGuard 稳稳扎根于**应用请求层**，为所有闭源商用 API（Anthropic/OpenAI/DeepSeek）提供最直接的成本缩减与上下文守护能力。

## 三、 核心请求生命周期（10 步链路）

```text
① 客户端请求入站 (POST /v1/chat/completions 或 /v1/messages)
       ↓
② 协议归一化 (Adapter)
       → 将 OpenAI / Anthropic 差异格式统一转为内部 NormalizedRequest
       ↓
③ 初始 Token 评估与自适应档位调度 (AdaptiveScheduler)
       → 估算 Prompt 大小，根据阈值动态激活 L0 / L1 / L2 / L3 压缩级别
       ↓
④ 虚拟工具本地拦截检测 (VirtualToolExecutor)
       → 若检测到模型请求调用 ctx_expand，本地直接查 SQLite 0ms / 0 Token 返回短路响应
       ↓
⑤ Prompt Cache 动态分区 (CacheGuard)
       → 反向映射已缓存 Token，严格切分 [Frozen Prefix] 与 [Compressible Suffix]
       ↓
⑥ 可逆指纹构建与活区压缩 (Compression Pipeline)
       ├─ DedupCompressor: 将历史重复文件/工具输出替换为 [Ref:sha256_...]
       ├─ ANSICleaner: 正则清洗终端控制符与颜色转义码
       ├─ ProgressMerger: 合并多帧构建进度条
       ├─ StacktraceFolder: 折叠连续重复异常堆栈 [Repeated N times]
       ├─ JSONStructCompressor: 对象数组提取 _schema 表头与 _rows 矩阵
       └─ WhitespaceCleaner: 清理多余空行与格式占位符
       ↓
⑦ 经济套利仲裁 (Economic Arbitrator)
       → 若压缩节省收益低于云端 Prompt Cache 读取折扣，自动回退原文以保全缓存
       ↓
⑧ 工具注入与 Cache 断点标记 (VirtualToolInjector & CacheGuard)
       ├─ 注入 ctx_expand 工具定义 (Sticky-On 保持)
       └─ 针对 Anthropic 自动注入 cache_control: {"type": "ephemeral"}
       ↓
⑨ 转发上游云端 API (Upstream Client)
       → 基于 httpx 异步连接池与 orjson 快速序列化转发
       ↓
⑩ SSE 流式解析、响应透传与账本落盘 (SSE Streamer & SavingsLedger)
       → 拦截流式输出，实时记录原始/压缩/缓存命中 Token 与资金节省明细入 SQLite
```

## 四、 核心架构模块分布

```text
ctxguard/                                    核心 Python 源码体系
├── proxy/               反向代理与协议网关
│   ├── server.py        FastAPI / Starlette 异步高性能主服务
│   ├── router.py        OpenAI / Anthropic 双向请求路由与分发
│   ├── upstream.py      上游连接池与长连接复用器
│   ├── sse.py           流式 SSE 解析、透传与 Token 实时计数
│   └── adapters/        OpenAI / Anthropic 格式双向归一化适配器
├── core/                核心上下文处理中枢
│   ├── pipeline.py      压缩算子流水线控制器
│   ├── context.py       统一 NormalizedRequest / RequestContext 数据结构
│   ├── adaptive_scheduler.py 自适应多档位压缩调度器
│   ├── semantic_cache.py     会话级与全局语义缓存
│   ├── guards/          Prompt Cache 守护者 (cache_guard.py)
│   ├── compressors/     六大结构化压缩算子 (dedup, json, ansi, stack, etc.)
│   └── virtual_tools/   虚拟工具注入器与 0 Token 本地拦截执行器
├── storage/             单文件嵌入式存储中枢
│   ├── db.py            SQLite 连接池与 WAL 并发模式管理
│   ├── repository_fingerprint.py  SHA-256 去重内容指纹库
│   ├── repository_graph.py        SQLite + FTS5 时序实体知识图谱
│   └── savings_ledger.py          双向 Token 与资金节省记账本
├── learn/               离线失败分析与自进化引擎
│   ├── loop_detector.py 死循环与重复查询检测算法
│   ├── causality_extractor.py     因果转折点提取
│   └── atomic_writer.py 标记块隔离规则落盘写入器
└── plugins/onnx/        可选: 微型双向编码器 INT8 语义打分剪枝插件
```

## 五、 三大架构硬性指标

1. **< 3ms 代理极低延迟**：采用 Rust 底层的 `orjson` 快速序列化与内存复用，除大模型本身推理网络开销外，网关处理开销 < 3ms；
2. **0 外部环境依赖**：单条 `pip install .` 命令即可启动，完全不需要 Docker 或独立数据库守护进程；
3. **100% 协议透明**：下游客户端无感，上游大模型 API 行为完全一致。
