# 11 · 踩过的坑与技术内幕 (Gotchas & Hard Lessons)

> 本文总结在真实生产环境与长会话 Agent 压测中踩过的 6 大核心深坑与应对方案。

---

## 踩坑 1：盲目压缩导致「缓存雪崩」，账单反增 5 倍

- **现象**：上线了文本摘要压缩后，发现云端 API 账单不仅没降，反而比原来高出了 3~5 倍！
- **根因**：压缩算法对第 2 轮的历史消息做了 10% 的微小词句替换，导致从第 2 轮往后的所有 Token 全部无法命中 Anthropic 的 90% 缓存折扣。
- **解法**：确立 **Cache First（缓存第一）** 原则，引入 `CacheGuard` 动态边界与经济套利仲裁，严禁破坏已缓存前缀。

---

## 踩坑 2：虚拟工具反复增删引发「Tools 翻转震荡」

- **现象**：同一会话中，偶数轮次命中缓存，奇数轮次全部 Cache Miss。
- **根因**：最初逻辑是“本轮压了数据才注册 `ctx_expand` 工具”。导致 `tools` 列表在有/无之间跳变，修改了头部字节。
- **解法**：实施 **Sticky-On 策略**——一旦开启，会话生命周期内永久挂载该工具。

---

## 踩坑 3：JSON 序列化微小差异摧毁字节级哈希

- **现象**：Prompt 内容明明没有改动，但云端仍判定为 Cache Miss。
- **根因**：Python 原生 `json.dumps()` 默认在分隔符后携带空格（`", "`），而不同客户端可能使用紧凑分隔符（`","`），或者 Unicode 中文进行了 `\uXXXX` 转义。
- **解法**：采用 `orjson` 进行 SIMD 级精确序列化，未修改的冻结消息直接按原始请求字节流重放。

---

## 踩坑 4：异常堆栈过度折叠导致 Agent 失去 Debug 能力

- **现象**：连续出现 10 次报错时，压缩器将堆栈全部折叠为 1 行，模型回答：“找不到具体报错代码行号”。
- **根因**：堆栈折叠算子过于激进，把第一次出现的完整 Traceback 关键信息也给合并掉了。
- **解法**：**首帧必留（First Frame Preserved）**——严格保留第 1 次异常的完整文件名、行号与局部变量，只折叠后续 9 次完全相同的重复堆栈。

---

## 踩坑 5：流式 SSE Chunks 缓冲区延迟累积

- **现象**：接入代理后，开发者明显感觉到打字机效果出现“卡顿与一顿一顿”的现象。
- **根因**：中间件对 chunk 进行了完整行的缓冲（Line-buffering）等待 `\n\n`。
- **解法**：在 `sse.py` 中采用无缓冲即时透传，流式字节在进入网关的瞬间立即向客户端 `yield`，将网关转发延迟压低至 **< 0.1ms**。

---

## 踩坑 6：Assistant 消息被压缩引发大模型 Prompt 模仿与幻觉

- **现象**：压缩历史后，大模型开始自发输出诸如 `[Ref:sha256_...]` 格式的文本，无法正常回复用户。
- **根因**：压缩算子修改了历史中 `role: "assistant"` 的发言，模型将该格式当作上下文学习范例进行了学习与模仿。
- **解法**：铁律红线——**所有压缩算子对 `role == "assistant"` 的消息绝对原样放行，严禁触碰**。

---

## 踩坑 7：会话中途写入自进化规则引发「前缀漂移雪崩」

- **现象**：长对话进行到 100+ 轮时，上一轮服务端缓存命中高达 11.6 万 Token，下一轮缓存命中瞬间断崖式跌落至 **0**！
- **根因**：后台自进化引擎（`ctxguard learn`）在第 949 轮提炼出了新的避坑经验规则并写入了 `AGENTS.md`，客户端（如 Pi-Agent）在发起下一轮对话时重新读取了修改后的规则文件，导致发给模型的 `System Prompt` 前缀发生了字节级变动。根据 Google Gemini / Anthropic Claude 服务端 KV Cache 的 **“最长公共前缀 (Bit-Exact Prefix)”** 匹配机制，首字节变动导致后续 10 万+ 历史对话的云端缓存全量失效！
- **解法**：实施 **【宏观前缀冻结 (Session Prefix Freeze) + 微观尾部热区注入 (Live Zone Tail Injection)】** 黄金组合：
  1. **会话级前缀冻结**：在 `CacheGuard` 中对首次建立会话的 System Prompt 与指令建立只读快照，会话存续期间 100% 回放锁定初始前缀，新规则仅对新开会话生效；
  2. **尾部热区注入**：会话中途产生的动态记忆或单轮实时避坑提示，严格只附加在最新一轮 User 消息的末尾（Live Zone），保障历史 10 万+ Token 缓存 0 扰动。

---

## 踩坑 8：模糊进程查杀 (`kill -9`) 误伤本地模型中转链路

- **现象**：在排查端口或重载网关时执行 `ps aux | grep ctxguard` 并直接 `kill -9`，导致下游客户端（Pi-Agent / Cursor）报错：`CtxGuard stream connection error: All connection attempts failed` (Connection Refused)。
- **根因**：开发机上除了 8787 端口的 CtxGuard 本地网关外，还在 8045 端口运行着为 Gemini / Claude 提供中转的本地核心进程（如 Antigravity Tools / 本地模型 Bridge），模糊 grep 命令将 8045 核心中转服务一并误杀，导致网关向上游转发流式请求时遭遇连接拒绝。
- **解法**：
  1. 明确端口分工边界：`8787` 为 CtxGuard 上下文网关，`8045` 为上游 Antigravity Tools 模型桥接；
  2. 运维与平滑重载采用精准进程过滤（如 `pgrep -f "ctxguard.cli.main start"`）与优雅停机（`SIGTERM`），并在文档与监控大盘中增加上游健康状态拨测指引。

---

## 踩坑 9：沙箱网络隔离机制导致的本地端口 (Localhost Socket) 连通性阻断

- **现象**：在特定安全沙箱环境或受限子进程中启动网关时，网关可以监听 8787，但在尝试向宿主机 `127.0.0.1:8045` 发起出站请求时报错 `[Errno 1] Operation not permitted`。
- **根因**：OS 层面的进程沙箱安全策略默认拦截了进程对宿主机本地回环端口的 TCP 跨进程连接。
- **解法**：在启动网关守护进程时确保赋予完整的宿主机网络访问权限（以 BypassSandbox / 独立系统守护进程方式运行）。
