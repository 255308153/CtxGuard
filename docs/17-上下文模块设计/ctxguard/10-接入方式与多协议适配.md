# 10 · 接入方式与多协议适配

## 一、 零侵入透明反向代理接入

CtxGuard 最大优势在于**零业务代码侵入**。任何支持配置 `base_url` 的客户端或框架均可秒级接入。

### 1. Claude Code 接入
```bash
# 启动 CtxGuard 守护网关
ctxguard start

# 设置环境变量将 Claude Code 指向本地代理
export ANTHROPIC_BASE_URL="http://127.0.0.1:8787"
claude
```

### 2. Pi Agent + Pi-Web 接入 (主流推荐)
在 `pi agent` 配置文件或环境中设置：
```bash
export OPENAI_BASE_URL="http://127.0.0.1:8787/v1"
export ANTHROPIC_BASE_URL="http://127.0.0.1:8787"
```
启动 `pi-web`（端口 30141）后，所有发出的 Agent 动作流、代码审查及工具调用，均由 CtxGuard 网关自动完成 Prompt Cache 防抖、冗余清洗与知识图谱记忆召回。

### 3. Cursor / VSCode 接入
在 Cursor 设置中：
- 将 OpenAI / Anthropic Base URL 配置为 `http://127.0.0.1:8787/v1`；
- API Key 填入任意字符串（或由 CtxGuard 在 `ctxguard.yaml` 中统一向上游注入）。

### 3. Python 官方 SDK (OpenAI / Anthropic) 接入
```python
from openai import OpenAI

# 仅需修改 base_url
client = OpenAI(
    base_url="http://127.0.0.1:8787/v1",
    api_key="sk-upstream-key",
)

response = client.chat.completions.create(
    model="gpt-4o",
    messages=[{"role": "user", "content": "Analyze codebase..."}]
)
```

## 二、 双向协议适配器架构 (`ctxguard/proxy/adapters/`)

CtxGuard 内置适配器模式（Adapter Pattern），无缝处理格式差异：
- `OpenAIAdapter`：处理 `/v1/chat/completions`、`functions` / `tool_calls`；
- `AnthropicAdapter`：处理 `/v1/messages`、`system` 顶层字段、`tool_use` / `tool_result` content blocks 以及 `cache_control` 断点；
- **非标接口透明转译器 (Transparent Transpiler)**：自动捕获第三方客户端发出的非标 `/responses` 或含有 `input` / `input_text` 的请求体，动态在网关内部转译为标准的 `/v1/chat/completions` 发往上游中转站，彻底消除中转站 `503 Service Unavailable` 或字段缺失报错，实现客户端 0 改动无缝接入。

## 四、 实战踩坑与排障记录 (Troubleshooting & Lessons Learned)

### 1. Codex / Responses 协议转译中的“界面输出空白” Bug (UI Blank Rendering)
- **现象描述**：
  客户端（如 Codex GUI / OpenCode）发来 `/backend-api/codex/responses` 请求，网关将中转站的 ChatCompletions 流转译并返回后，客户端界面不报错却**呈现一片空白（无文本打字输出）**。
- **根本原因**：
  基于 Rust/TypeScript 构建的 Codex 客户端并非直接消费文本流，而是遵循严格的 **DOM 事件树挂载协议**：
  1. 必须先通过 `response.output_item.added` 初始化消息容器；
  2. 紧接着必须发送 `response.content_part.added` 初始化文本段落挂载点（含 `item_id`、`content_index`）；
  3. 后续的 `response.output_text.delta` 才能挂载到该节点并触发 UI 重绘。若缺失 `content_part.added` 或缺少 `item_id` 关联，客户端会判定无挂载目标直接丢弃文本块，导致界面全白。
- **修复方案 (`ctxguard/proxy/sse.py`)**：
  严格对齐 OpenAI Responses 与 Headroom 的事件层级规范，按序生成完整的生命周期事件：
  `response.created` ➔ `response.output_item.added` ➔ `response.content_part.added` ➔ `response.output_text.delta` ➔ `response.completed`。

### 2. 状态码双阶段探测防解码崩溃 (Stream Transport Error)
- **现象描述**：
  上游或中转站返回 `4xx/5xx`（如 401 密钥失效、429 限流、502 宕机）时，客户端报错：`Transport error: network error: error decoding response body`。
- **根本原因**：
  上游发生错误时返回的是非流式 JSON 报文，如果网关未探测状态码直接包裹 `StreamingResponse` 返回，客户端的流式解包器（如 Rust `reqwest` / SSE Parser）在尝试解析 JSON 为 SSE 帧时会触发致命解码崩溃。
- **修复方案 (`ctxguard/proxy/router.py`)**：
  在建立长连接前增加**状态码前置探针**。当 `status_code >= 400` 时立即阻断流通道，直接透传原生 JSON 报文与真实 HTTP 状态码。
