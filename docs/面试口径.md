> **用途**：把「CtxGuard 上下文优化与智能守护网关」以最清晰、最硬核的方式讲给面试官听。
> **原则**：先给直觉与业务痛点 → 再给量化数据与核心机制；说得出**技术权衡与系统边界**（我做了什么 / 为什么这么选型）。

## 1. 三十秒极简介绍（当面试官说"先简单介绍一下你的上下文优化项目"）

> "在开发 Coding Agent 和多轮对话系统时，我发现上下文开销有两个致命瓶颈：
> 1. **Token 浪费极其严重**：Agent 频繁重复读取相同文件、工具返回大量同构 JSON 冗余 Key 和终端 ANSI 乱码，每轮多花 60% 以上的无用 Token；
> 2. **破坏厂商 Prompt Cache**：很多开源压缩方案粗暴截断历史消息，导致 Anthropic / DeepSeek 官方 90% 的前缀缓存折扣完全失效，账单反而翻倍。
> 
> 为此我主导设计并实现了 **CtxGuard（上下文守护网关）**。
> 它是一个极致轻量（0 重型依赖、单文件免运维、<3ms 转发延迟）的本地代理网关，融合了业界顶尖的 5 项技术：
> 1. **Prompt Cache 守护（借鉴 Headroom）**：基于 Token 边界反向推导与字节级防抖，确保命中 90% 云端前缀缓存；
> 2. **可逆无损压缩（借鉴 sqz）**：基于 SHA-256 指纹去重，向模型注入 `ctx_expand` 工具并在网关层**本地 0 Token 拦截展开**；
> 3. **结构化算子流水线**：实现同构 JSON 数组 Schema 提取与行矩阵化（无损压 48%）、ANSI 与重复堆栈智能清洗；
> 4. **多档自适应与轻量剪枝（借鉴 Kompact 与 LLMLingua-2）**：短上下文走规则，超长上下文触发 INT8 ONNX 双向编码器语义剪枝；
> 5. **离线自学习与规则落盘**：后台异步挖掘 Agent 死循环与因果转折点，幂等沉淀到 `CLAUDE.local.md` 规则库。"

## 2. 高频深度技术追问标准回答

### Q1：你们如何解决“压缩省了 Token 但破坏了 Prompt Cache 导致账单更贵”的问题？

> **答题思路**：先讲原理，再亮出公式与算法实现。
> 
> "这是我们在项目中确立的第一性原理：**Cache > Compression（缓存优于压缩）**。
> 
> Anthropic 和 DeepSeek 提供了 90% 的 Prompt Cache 读取折扣（即命中缓存只收 0.1 倍价格），但要求前缀必须从第 1 个字符开始严格逐字节完全一致。如果你在历史对话中修改了一个词，后面全部全价重算。
> 
> CtxGuard 采取了三项硬核保全机制：
> 1. **动态 Token 冻结边界反算（Dynamic Token Boundary Mapping）**：上游响应只返回 `cache_read_tokens`，CtxGuard 通过正向累加历史消息的 Token 数量，精确反推出 `frozen_message_count`，将消息分为 `[Frozen Prefix 冻结前缀]` 和 `[Compressible Suffix 活区尾部]`，算子仅对未被缓存的活区动刀；
> 2. **覆盖式字节防抖（Overlay Cached Prefix）**：由于不同 JSON 序列化器存在空格或 Unicode 转义微小差异，CtxGuard 缓存上一轮实际转发的原始对象，新请求的冻结前缀直接重放，确保 SHA-256 绝对一致；
> 3. **经济套利仲裁器（Economic Arbitrator）**：内置公式：
>    $$\text{savings\_fraction} = \frac{\text{raw} - \text{compressed}}{\text{raw}} > \text{read\_discount}$$
>    只有当压缩节省率高于云端读取折扣（如 Anthropic 的 90%）时，才允许对边界尝试重压缩，否则绝对回退原文保全缓存。"

### Q2：可逆压缩（Reversible Dedup）如何做到 0 Token 开销还原？

> **答题思路**：讲解生命周期与网关本地短路拦截。
> 
> "传统的压缩是有损的，一旦丢了关键信息模型就产生幻觉。CtxGuard 实现了 **CCR（Compress-Cache-Retrieve）闭环**：
> 1. **指纹录入**：当 Agent 首次读取大文件或工具输出时，CtxGuard 在本地 SQLite 记录全文及其 SHA-256；
> 2. **指纹替换**：当后续轮次再次出现完全相同的内容时，替换为紧凑标记：`[Ref:sha256_e4d909 | File: src/main.py | 350 lines unchanged]`（仅消耗 ~15 Token）；
> 3. **虚拟工具注入**：在 tools 列表中声明 `ctx_expand(ref_id)`；
> 4. **本地短路拦截**：如果大模型在推理中认为需要查看代码细节，它会发起 `tool_use: ctx_expand`。**CtxGuard 在网关入口直接拦截该请求，从本地 SQLite 取出原文组装为 tool_result 立即返回给模型，根本不向上游云端大模型转发这一轮开销**！
> 5. 这样既享受了 90% 以上的日常 Token 削减，又保证了 100% 的信息无损可恢复。"

### Q3：你们在工具注入时踩过什么隐蔽的坑？

> **答题思路**：讲 Tools Flipping（工具翻转震荡）以及 Sticky-On 方案。
> 
> "最开始我们的逻辑是：'只有当前轮次发生了指纹压缩，才向 `tools` 注入 `ctx_expand` 工具'。
> 这导致了一个严重的缓存震荡（Tools Flipping）：
> - 第 1 轮：没压文件 → `tools = [read, grep]`
> - 第 2 轮：压了文件 → `tools = [read, grep, ctx_expand]`
> - 第 3 轮：没压文件 → `tools = [read, grep]`
> 
> 整个 `tools` 数组在两个状态间反复跳变。因为 `tools` 定义处于 Prompt 头部，只要它变了，**从 `tools` 往后的所有历史对话和 System Prompt 缓存全部作废**！
> 
> 我们的修复方案是 **Sticky-On（一次开启，永久挂载）**：只要当前会话发生过一次 CCR 压缩，`ctx_expand` 工具在后续所有轮次始终注入，彻底消除头部字节抖动。"

### Q4：为什么你们坚持 0 外部重型依赖，而不是用 Redis + Milvus？

> **答题思路**：突出工程架构的极致轻量与 <3ms 极低延迟要求。
> 
> "三个维度的考量：
> 1. **开发者体验与部署成本**：本地运行 Agent 时，要求开发者在本地启 Docker、配 Redis/PostgreSQL 门槛过高。CtxGuard 实现单命令 `pip install .` 即开即用；
> 2. **读写性能与并发**：SQLite 在 `WAL`（Write-Ahead Logging）模式下，单连接只读性能超过 50,000 QPS，毫秒级响应，完全能支撑本地网关的高频存取；
> 3. **精准匹配与图谱结合**：针对代码符号和实体，我们采用 **FTS5 BM25 全文索引 + BFS 2 跳子图遍历**，配合 `valid_from` / `valid_until` 的时序演化链（Supersession Chain），内存开销不足 50MB，且没有向量库冷启动与索引重建开销。"

## 3.  架构加分项：系统演进与团队分工

被问到“如果让你带 3~4 人的团队继续迭代这个系统，你如何分工与规划？”：

> "我会把系统清晰划分为三条演进线：
> 1. **网关与协议基础设施（1人）**：深耕 FastAPI/Starlette 异步代理、`orjson` SIMD 序列化优化、SSE 字节级透明透传、以及对 OpenAI/Anthropic/Gemini 新特性的探针监控；
> 2. **结构化算子与智能剪枝流水线（1~2人）**：完善 AST 语法级代码剪枝（函数折叠与签名保留）、JSON 动态嵌套折叠、以及 ONNX INT8 微型双向编码器的轻量量化与性能调优；
> 3. **记忆存储与自进化规则挖掘（1人）**：完善单文件图谱记忆的时序衰减算法，扩展死循环检测状态机，建立离线自动化评测集（基于 GSM8K / HumanEval 评估压缩率与精度损耗）。
> 
> **技术底线**：上下文优化必须下沉为通用的网关基础设施，业务 Agent 逻辑千变万化，但不能让每个业务开发手工去写 Prompt 截断代码。"
