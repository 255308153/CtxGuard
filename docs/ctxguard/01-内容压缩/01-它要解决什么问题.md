# 01 · 它要解决什么问题

## 一、 Agent 运行时的真实 Token 浪费构成

在 Coding Agent（如 Cursor / Claude Code）以及工具调用工作流中，上下文 Token 的膨胀并非来自思考过程，而是被大量**高度重复且低信息密度的结构噪音**所占据：

```text
实际测试中 Coding Agent 上下文 Token 分布统计：
┌────────────────────────────────────────────────────────────┐
│ ■ 重复读取的代码文件全文 (40%~60%)                          │
│ ■ 工具返回的同构 JSON 字典大数组 (20%~30%)                  │
│ ■ 终端构建 ANSI 颜色码、无意义进度条与重复堆栈 (10%~15%)    │
│ □ 真正的用户指令与核心代码变更 (仅占 10%~15%)               │
└────────────────────────────────────────────────────────────┘
```

---

## 二、 三大典型冗余案例剖析

### 1. 痛点一：多轮工具调用中的重复文件读取
Agent 在第 1 轮通过工具读取了 `src/server.py`（1,000 行，约 4,500 Token）。在第 3 轮和第 5 轮中为了排查 Bug 又重新执行了读取操作。
- **后果**：同一个 4,500 Token 的文件在上下文历史中出现了 3 次，白白消耗 13,500 Token，占用了超大窗口。

### 2. 痛点二：JSON 同构对象数组的 Key 膨胀
数据库查询或 API 工具返回 100 条相同结构的记录时，每一个 JSON 对象都完整携带了冗余的键名：
```json
[
  {"user_id": 1001, "username": "alice", "email": "alice@corp.com", "role": "admin"},
  {"user_id": 1002, "username": "bob", "email": "bob@corp.com", "role": "developer"},
  ... (重复 100 次相同的 4 个 key)
]
```
- **后果**：键名字符占据了 50% 以上的体积，严重稀释了大模型的注意力并浪费成本。

### 3. 痛点三：终端 ANSI 颜色转义与进度条轰炸
执行 `npm install` 或 `pytest` 时，终端输出包含海量 ANSI 颜色码（如 `\x1b[32m`）以及不断刷屏的下载进度条。
- **后果**：几百行无效的终端控制字符塞进 Prompt，容易诱发模型输出格式异常或乱码。

---

## 三、 CtxGuard 的解决策略

CtxGuard 在 `ctxguard/core/compressors/` 中实现了针对性的六大结构化算子：
1. **DedupCompressor**：SHA-256 指纹替换重复文件，配合 `ctx_expand` 虚拟工具实现 100% 可逆；
2. **JSONStructCompressor**：同构数组提取 `_schema` 表头与 `_rows` 矩阵，无损压缩 48% 以上；
3. **ANSICleaner & ProgressMerger & StacktraceFolder**：正则智能清洗终端噪音。
